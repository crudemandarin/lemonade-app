## 1. Decisions (from the user)

1. **Legacy accounts: claim on first sign-in.** After Google sign-in, a player can enter their old username once to link it, and their runs, scores and game carry over. First come, first served (the old login let anyone type any name, so this has a known hijack risk; document it).
2. **Public identity is the username.** Google name and email are never shown or returned by any API. New players choose a username on first sign-in, under the existing rules (`normalizeUsername` in `internal/api/game.go`: trimmed, lowercased, 3 to 40 printable ASCII characters, no spaces; unique, case-insensitive). Do not prefill it from the Google name or email.
3. **Dev and tests: Firebase Auth Emulator plus a dev-only bypass.** Local and CI use the emulator for real token flows. A backend `AUTH_MODE=dev` accepts the old `X-Username` header for fast tests and is **refused in production**.

Not decided by the user, recommended here (change only with their approval): no `both` mode in production (after cutover, username-only login is gone); popup sign-in with redirect fallback; no Firebase Admin credentials file (Cloud Run's default identity is enough for token verification).

## 2. Current state (verify before relying on it)

- Backend: `POST /api/login {username}` creates or gets a user and their first game; `requireUser` in `internal/api/game.go` reads `X-Username`, calls `repo.FindUser(username)` and puts the user in the gin context. All handlers use `currentUser(c).ID`, and runs, scores and games are keyed by user id, so **only identity resolution changes, not game logic.** `userRow{ID, Username unique, CreatedAt}` in `internal/store/postgres.go`; `FindUser` and `CreateUserWithGame` in `store/repository.go`, `postgres.go`, `memory.go`. `libraries/secrets.go` loads env vars.
- Frontend (Angular 17, signals): `core/session.service.ts` (username in localStorage), `core/username.interceptor.ts` (sets `X-Username`), `core/unauthorized.interceptor.ts` (clears session on 401), `core/auth.guard.ts` (username present or go to `/signin`), `core/game.store.ts` `signIn` and `signOut`, `pages/signin`, `pages/home`. Same-origin: nginx (`lemonade-web/nginx.conf.template`) proxies `/api` to the api, so no CORS.
- Infra: Terraform in `deploy/infra/*.tf` (Cloud Run web and api, Cloud SQL, Secret Manager, Artifact Registry). The GCP project id is a variable (`project_id`, default recently changed to `lemonade-app-dev`); GitHub Action redeploys on pushes to `main` touching `lemonade-api/**` or `lemonade-web/**`.

## 3. Target design

**Flow:** Google popup sign-in (Firebase JS SDK) gives a Firebase ID token. The SPA sends it as `Authorization: Bearer <token>` on every API call. The API verifies it, maps `uid` to a user row, and continues as today. A signed-in player with no user row is sent to onboarding to either **choose a username** or **claim a legacy one**.

### Backend (`lemonade-api`)

- **`TokenVerifier` interface** (new package, e.g. `internal/auth`): `Verify(ctx, idToken) (Identity{UID, Email, EmailVerified, Provider}, error)`. Implementations: Firebase (Admin SDK `firebase.google.com/go/v4`, `auth.Client.VerifyIDToken`, configured with `FIREBASE_PROJECT_ID`; verifies signature, `iss`, `aud`, `exp`), and a fake for tests. Additionally require `firebase.sign_in_provider == "google.com"` and `email_verified == true` (reject other providers even if enabled later). Do not call `VerifyIDTokenAndCheckRevoked` (extra network call per request; tokens live 1 hour, accepted). Confirm the module supports the repo's Go toolchain (`go.mod` says Go 1.27) before committing to it; if not, verify with the public keys directly and note it in DECISIONS.
- **`AUTH_MODE`** env: `firebase` (default) or `dev`. `dev` additionally accepts `X-Username` (existing behavior) and keeps `POST /api/login`. **Startup must fail** if `AUTH_MODE=dev` while running on Cloud Run (`K_SERVICE` set) or `APP_ENV=production`, and fail if `AUTH_MODE=firebase` and `FIREBASE_PROJECT_ID` is empty. Unit-test both refusals. In `firebase` mode `/api/login` returns 404 (route not registered).
- **Emulator:** the Admin SDK honors `FIREBASE_AUTH_EMULATOR_HOST` automatically (tokens are unsigned; verification works with a `demo-*` project id).
- **Middleware:** `requireUser` becomes: dev mode with `X-Username` header uses the old path; otherwise read the bearer token, verify, `repo.FindUserByUID(uid)`. Errors: 401 `unauthorized` (missing, malformed, expired, invalid token); 403 `profile_required` (valid token, no user row) with the identity available to the profile endpoints only. Keep `/api/health` public. Keep `scores` and `runs` behind `requireUser`.
- **Profile endpoints** (use a lighter middleware `requireIdentity` that verifies the token but does not require a user row):
  - `GET /api/me` returns `{username, id}` or 403 `profile_required`.
  - `POST /api/me/username {username}` creates the user and their first game atomically (`CreateUserWithGame` extended to take the UID and email). 400 `invalid_username`, 409 `username_taken`, 409 `already_linked` if the UID already has a profile.
  - `POST /api/me/claim {username}` links an existing legacy user: allowed only if that user exists and has no `firebase_uid`, and the caller's UID has no profile. Do it in one transaction with a conditional update (`WHERE firebase_uid IS NULL`) so two simultaneous claims cannot both win. 404 `unknown_username`, 409 `already_claimed`, 409 `already_linked`. Rate limit claims per UID (simple in-memory limiter is fine, note it is per instance). Record `claimed_at`.
  - No account deletion, no email change, no multiple Google accounts per player in this slice (Future work in `PLAN.md`).
- **Store:** `AutoMigrate` adds to `users`: `firebase_uid` (string, nullable, unique index; Postgres allows many NULLs), `email` (string, nullable, private, lowercased, **never included in any DTO**), `claimed_at` (nullable). New methods `FindUserByUID`, `CreateUserWithGame(ctx, username, uid, email, game)`, `ClaimUser(ctx, username, uid, email)`. Mirror all in `memory.go`, and extend the store contract test so both implementations behave the same (unique uid, claim race, NULL handling). Run the real-Postgres test with an old-shape `users` row: `DATABASE_URL="postgres://admin:password@localhost:5432/sample?sslmode=disable" go test ./internal/store`.
- **Config:** add `AuthMode`, `FirebaseProjectID` to `libraries/secrets.go` (or a small config struct) and to `.env.example`.

### Frontend (`lemonade-web`)

- Use the **Firebase JS SDK directly** (modular `firebase/app`, `firebase/auth`), not `@angular/fire`, to avoid Angular 17 version coupling. Pin a current v10 or v11 release; check bundle size impact (`npm run build` budgets).
- **`core/auth.service.ts`**: wraps the SDK. Signals: `firebaseUser`, `ready` (true after the first auth-state event; use `authStateReady()` or the first `onAuthStateChanged`), `profile` (`{username}` or null). Methods: `signInWithGoogle()` (popup; on `auth/popup-blocked` or a standalone PWA/mobile context fall back to `signInWithRedirect`), `signOut()`, `getIdToken()` (the SDK caches and refreshes; never store tokens yourself), `loadProfile()`, `createProfile(username)`, `claim(username)`. Firebase persists the session in IndexedDB.
- **`core/auth.interceptor.ts`** replaces `username.interceptor.ts`: attaches `Authorization: Bearer <token>` to `/api` requests. On 401 refresh the token once (`getIdToken(true)`) and retry; if it still fails, sign out. `unauthorized.interceptor.ts` keeps its role but clears the Firebase session too. On 403 `profile_required` navigate to onboarding (do not sign out).
- **`SessionService`** becomes a thin view over `AuthService` (keep the `username` signal so existing components and specs change minimally; stop reading and writing `lemonade.username`; clear the old key on load).
- **Guard:** `authGuard` waits for `ready`, then: signed out goes to `/signin`; signed in with no profile goes to `/signin/username` (onboarding); ready goes on. Cover the loading flash (a small spinner, no redirect flicker).
- **Pages:** `/signin` has one primary button, "Continue with Google". `/signin/username` (onboarding): choose a username field with the same validation and error copy as today, and a secondary "I already have a username" path that calls claim (explain that this links the old account). Show `username_taken`, `unknown_username`, `already_claimed` errors inline. Nav bar shows the username and a sign-out action. Sentence-case copy, one primary button per screen, works at 390 px.
- **Runtime config:** the same image is deployed to different GCP projects (the project id already changed once), so avoid baking Firebase settings at build time. Follow how `nginx.conf.template` is rendered at container start and generate `/config/firebase-config.json` (`apiKey`, `authDomain`, `projectId`, `appId`, optional `useEmulator`, `emulatorUrl`) from env vars, fetched at bootstrap before the app starts. **Do not put it under `/assets/**`**: the `assets` group in `ngsw-config.json` prefetches and caches that path, so after a redeploy to another project the service worker could serve a stale config. Serve it from a path no `assetGroups` pattern matches, send `Cache-Control: no-store` for it in `nginx.conf.template`, and add a spec or check that the built `ngsw.json` does not list it. Firebase web config values are not secrets. If `useEmulator`, call `connectAuthEmulator`.
- **PWA and popup gotchas:** `ngsw-config.json` already excludes `/**/*__*` and `/**/*__*/**` from `navigationUrls`, so `/__/auth/*` is not handled by the service worker: keep those exclusions and verify with a production build (the service worker is off in `ng serve`); there are no `dataGroups` today, so do not add ones that would match Google or Firebase hosts; do not add a `Cross-Origin-Opener-Policy: same-origin` header (it breaks popup sign-in; `same-origin-allow-popups` is fine). For the redirect fallback to work with third-party-storage restrictions, `authDomain` must be same-origin: proxy `/__/auth/` and `/__/firebase/` in nginx to `<project>.firebaseapp.com` and set `authDomain` to the app's own host. Verify installed-PWA sign-in on desktop Chrome (the user has verified PWA install before).

## 4. Security notes to document

- Verification is stateless per request (local signature check against cached Google keys); the DB lookup by `firebase_uid` replaces the old username lookup and needs the unique index.
- Bearer tokens only in the `Authorization` header, never in URLs or logs. Do not log tokens or emails.
- Claim is first come, first served; legacy usernames are effectively public, so a hostile user could claim someone else's before they do. Put this in README "Known limitations" and `numeric-tdd.md`, replacing the current "auth is intentionally weak" text (SPEC rule 22 and decision 19 are revised: add a DECISIONS entry). Optional future hardening: a claim deadline after which unclaimed legacy accounts are archived.
- The leaderboard and run records show usernames only. No endpoint returns email or Google name.
